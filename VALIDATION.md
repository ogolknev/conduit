# Проверка Conduit 0.2.8 — 6 ноября 2026

Проверено локально на Apple Silicon, Swift 6.2.4 / Command Line Tools:

- Mac: release-сборка с IOBluetooth и описанием разрешения Bluetooth в Info.plist.
- Android: APK versionCode 6 / 0.2.8; minSdk 26, targetSdk 35; подписи v2 и v3
  проверены apksigner. Ключ разработки тот же, что у компаньона 0.1.
- 20 Swift-тестов в четырёх наборах прошли: обработка потоков, фрагментация сообщений,
  кириллица / emoji, формат исходящего буфера, лимиты, JSON, ADB-состояния,
  подпроцессы и таймауты, файловые ID, пустые файлы, последовательность частей,
  защита от переполнения, SHA-256 и удаление незавершённой загрузки.
- Добавлены регрессионные проверки отсутствующего / устаревшего выбора телефона, запрета Bluetooth, выключенного адаптера, отсутствующего / неверного кода и повторного подключения без нового кода.
- JVM-проверка PairingCode прошла: одноразовый код, срок действия, три попытки,
  только ASCII-цифры, отзыв кода. Проверяется тот же класс, который входит в APK.
- 11 регрессионных сценариев Bluetooth-разрешений прошли: обычное соединение
  без ADVERTISE, отдельные разрешения для обнаружения, актуальное состояние
  разрешений после неполного ответа, Android 8–11 без нового runtime-запроса.
- Зависимости Shizuku 13.1.5 и аннотации проверены по закреплённым SHA-256.
- Комплектность: APK внутри Mac-приложения и ZIP совпадает с отдельным APK;
  сервер scrcpy в APK и Mac-сборке совпадает с закреплённым SHA-256.
- codesign --verify --deep --strict: действительная подпись ad hoc.
- Manifest APK: Bluetooth CONNECT / ADVERTISE, нет INTERNET, геопозиции,
  Accessibility, BLUETOOTH_SCAN и доступа ко всем файлам.
- Новый интерфейс Mac отрисован и просмотрен в отключённом состоянии.
  Отрисовка не запускает поиск устройств, ADB или сопряжение.

**Пока не подтверждены:** уведомления / ответы,
передача файлов и штатного установочного
ZIP, работа Shizuku / Binder-дескрипторов / привилегированного сервера на прошивке,
экран блокировки, Doze, расход батареи, восстановление после потери связи и перезагрузки.

## Проверка на устройствах 6 ноября 2026

Устройства: Mac Apple Silicon, macOS 26.6.2 (25G83); сопряжённый Xiaomi 15,
Android SDK 36. Пользователь установил APK 0.2.3. Диагностика телефона подтвердила
CONNECT / ADVERTISE, включённый адаптер, foreground-службу и `listener.ready`.

Первоначальный SDP-поиск Mac возвращал 23 службы без Conduit. Это не оказалось
доказательством отсутствия слушателя на телефоне: macOS возвращала старый каталог.
После разрыва и восстановления соединения только с Xiaomi число служб выросло
до 24, Conduit найден на RFCOMM-канале 17. Номер динамический, в приложении не закреплён.
Системное сопряжение и настройки адаптера не менялись.

Это соответствует измерениям автора
[aio-rfcomm для macOS 26.6.2](https://dlech.github.io/aio-rfcomm/known-bugs/).
Прямой адресный SDP-запрос и прямой L2CAP/SDP-запрос в отдельных диагностических
процессах не вернули callback за ограниченное время; они в рабочий путь не включены.

В следующей пользовательской попытке RFCOMM открылся успешно, но приложение
остановилось на `getEncryptionMode() == 0`. Проверка адреса реализации этого
метода в загруженном IOBluetooth на данном Mac показала ARM64-инструкции
`mov w0, #0; ret` (байты `00 00 80 52 c0 03 5f d6`). Таким методом нельзя
определить состояние шифрования. На том же открытом канале явный вызов
`requestAuthentication()` завершился с `kIOReturnSuccess` при нулевом результате
старого getter. Похожая замена описана в
[исправлении Edgepad](https://github.com/akshit-bansal11/edgepad/blob/main/CHANGELOG.md#350---2026-10-21).

## Проверка 0.2.4

Release-сборка и 20 Swift-тестов проходят. Добавлены ожидание готовности адаптера,
установка базового соединения до SDP, одно восстановление каталога при ручном
подключении, проверка номера открытого канала и явная аутентификация живой связи.
При автоматическом переподключении принудительное отключение телефона запрещено.
Код / токен / прикладные данные отправляются после аутентификации Bluetooth;
защищённый Android-слушатель не заменялся на insecure-вариант.

Проверен именно новый рабочий класс BluetoothChannel из release-бандла:
`--bluetooth-link-check` вернул `authenticated-rfcomm`, `applicationDataSent:false`.
Журнал содержит `sdp.services count=24`, успешный `rfcomm.callback` и
`rfcomm.authentication.result native=0x00000000`. После теста канал закрыт,
коды / токены / буфер / файлы не передавались. Эта проверка подтверждает транспорт
до прикладной авторизации, а не весь сценарий синхронизации.

Mac 0.2.4 установлен в `/Applications/Conduit.app` и запущен. Предыдущая версия
сохранена для отката. APK внутри обновления остаётся 0.2.3, протокол — 2.

После установки пользователь подключился по свежему коду: в журнале 12:47:00 UTC
есть `application.auth new-pair` и `connection.ready`. Обработка `ready` сохраняет
новый токен в Keychain до установки признака готовности. Пользователь подтвердил
подключение и отдельную проверку буфера: текст, скопированный на Mac, вставился
на телефоне. При этом Conduit на телефоне оставался открытым; тест не подтверждает
обратный автоматический буфер, фоновую работу, файлы или уведомления.

## Повторное подключение и простой в 0.2.5

Пользователь подтвердил ручной буфер Android → Mac. Затем сообщил о разрыве и
невозможности восстановить связь. В журнале Mac найдены повторяющиеся потери
по heartbeat после нескольких минут соединения и попытки открыть канал без
callback. Диагностика телефона подтверждает новый запуск службы в 13:00:38 UTC;
каталог Mac по-прежнему содержал 24 службы. Эти данные не устанавливают причину
перезапуска Android-процесса и не доказывают, что каждый разрыв вызван App Nap.

Исправлен реальный ложный вывод в проверке: ранее первый вызов таймера после
долгой паузы немедленно закрывал соединение по возрасту старого pong. Теперь
после паузы более 20 секунд отправляется новый ping с окном ответа 35 секунд.
Активная связь регистрирует userInitiatedAllowingIdleSystemSleep activity.
Добавлены ограничение частоты автоматического обновления каталога, backoff
повторов и сохранение настройки / намерения подключения.

25 Swift-тестов в пяти наборах прошли. Пять новых проверок охватывают настоящий
таймаут, паузу / пробуждение / смену часов, входящие сообщения и новую сессию,
рост задержки повторов и общий лимит обновления каталога между попытками.
Новый release-транспорт снова проверен на Xiaomi: authenticated-rfcomm,
applicationDataSent:false. Mac 0.2.5 установлен и запущен; APK остаётся 0.2.3.

После запуска 0.2.5 приложение восстановило сохранённую связь без нового кода:
13:09:46 UTC — `application.auth remembered-pair`, 13:09:52 — `connection.ready`.
За следующие 241 секунду зарегистрированы 23 ответа heartbeat, без потери связи,
таймаута и повторного подключения. Большинство последующих ответов пришли
за 0–1 секунду; первый — через 14 секунд. Это ограниченное наблюдение, а не
доказательство длительной надёжности или работы при выключенном экране / Doze.

Пользователь включил Shizuku и подтвердил надпись «Автобуфер через Shizuku
подключён». Первая попытка копирования не дала видимого результата, следующая
сработала автоматически. Это подтверждает прохождение события Android → Mac
через Shizuku, но не объясняет первую задержку. В реализации нет начального
запроса текущего содержимого буфера; подписка получает новые изменения после
запуска слушателя. Первое копирование могло предшествовать его запуску.

## Подробная диагностика, ADB и блокировка экрана в 0.2.8

Пользователь разрешил ADB; обновления установлены на подключённый Xiaomi через
`adb install -r`. Оба приложения — 0.2.8. Системное исключение из оптимизации
батареи не включалось автоматически: последнее состояние false. Фоновая служба,
Shizuku-права и сохранённая авторизация Bluetooth восстановились. Частичный
wake lock наблюдался в состоянии held при подключённом Mac.

27 Swift-тестов в шести наборах прошли. Новые проверки архива Android охватывают
два снимка, права 0600 и отказ до записи при неверном заголовке / превышении
лимита. JVM-проверки PairingCode, 11 сценариев разрешений и DiagnosticText прошли;
DiagnosticText проверен на отсутствие секретных сообщений исключений, кадры стека,
ограничение размера и корректное обрезание UTF-8.

Автоперенос фактически проверен: Android-отчёт получен по Bluetooth при подключении,
затем повторно по минутному таймеру. На Mac появились android-latest.log,
android-previous.log и combined-latest.txt с правами 0600. В журналах отмечены
clipboard.auto.event, tx.done.clipboard, clipboard.applied.mac и обратные ACK;
использованный тестовый текст в журналы не попал.

Для контролируемой проверки использовался временный shell-процесс с тем же
закреплённым scrcpy wrapper: он записывал только заранее известный тестовый текст
и возвращал признаки совпадения, без вывода содержимого буфера. При разблокированном
телефоне и свёрнутом Conduit Android → Mac дал точное совпадение. При погашенном
экране, пока keyguard ещё не был заблокирован, передача тоже прошла. После полной
блокировки запись теста прошла, а чтение вернуло null; текст на Mac не появился.
Это соответствует getPrimaryClip в Android 16, проверяющему isDeviceLocked.

Проверка обнаружила ошибку первого восстановления в 0.2.7: USER_PRESENT доходил
и запрос выполнялся, но scrcpy игнорировал GET_CLIPBOARD при autosync=true.
В 0.2.8 разовое чтение перенесено в Shizuku-сервис: загружается только JAR с
закреплённым SHA-256, после проверки он read-only; вызов wrapper выполняется
через основной Looper и ограничен тремя секундами. Ошибка чтения не останавливает
основную подписку. После разблокировки и обновления последний тест, пропущенный
при блокировке, автоматически восстановился на Mac с точным совпадением;
в журнале появились clipboard.snapshot.event и clipboard.mac.applied.
Отдельный полный цикл USER_PRESENT уже на 0.2.8 после этого не повторялся:
доставка события подтверждена на 0.2.7, исправленный RPC — при старте 0.2.8.

Длительный Deep Doze, работа без USB / зарядки, расход батареи, восстановление
после перезагрузки и новые передачи файлов / уведомлений остаются непроверенными.

Обратный контрольный тест 0.2.8: известный текст скопирован на Mac и доставлен
на Android через Conduit; проверка shell-wrapper вернула точное совпадение при
locked=false. Таким образом, обе стороны проверены на заранее известных данных.
Телефон в этих проверках подключён по USB / питанию; это не тест автономного Doze.


## 0.3.0 — интерфейс Mac и Android

- Общая монохромная палитра, системная светлая / тёмная тема, три раздела,
  отдельные настройки соединения, разрешений и диагностики.
- Симметричный знак приложения на сетке 24 × 24. Одинаковая видимая толщина
  1,5 pt / dp для навигационных и функциональных иконок. Масштабирование
  Android исправлено на равномерное с центрированием.
- Android: Java / D8 / AAPT2, ресурсы обеих тем и APK с подписью v2 / v3 собираются.
  Пакет dev.conduit.bridge, versionCode 7, versionName 0.3.0; ключ обновления сохранён.
- macOS: release-сборка SwiftUI / AppKit с новой ICNS-иконкой, встроенным APK,
  проверкой ресурсов --smoke-test и ad-hoc подписью.
- 27 Swift-проверок и Java-проверки кода сопряжения, разрешений (11 сценариев)
  и приватности диагностики проходят.
- Реальные SwiftUI-представления отрисованы и просмотрены: подключённое и
  отключённое устройство, тёмная тема, файлы и настройки при ширине 860 pt.
  Для изображений используется тестовая модель без соединения и реальных данных.
- Android-устройство в этом сеансе отсутствует. Новый интерфейс и взаимодействие
  с системными окнами на телефоне не проверены; APK не установлен на телефон.
  Функциональные испытания Bluetooth / Shizuku выше относятся к 0.2.x.
